## Route decisions pending staging

- Keep TikTok keyword and Threads recent as provisional baselines. TikTok Top and Threads top are comparison candidates. Prefer the best direct-match precision and reference recall under the same one-page cost and latency constraints. Preserve the baseline if the evidence is inconclusive.
- Instagram keyword search is the documented replacement candidate for phrase discovery. Validate normalization, local date filtering, coverage warnings, and actual costs with a bounded request. Keep Facebook limited to explicit hashtags. Continue evaluating YouTube, Reddit, and LinkedIn under the documented benchmark parameters.
- Validate X separately before counting it as active coverage. Check index coverage, normalization, the scheduled collection behavior and cursors, and actual credits. Keep general web off until there is a verified route. Index-backed platform results should retain their coverage metadata.

If the original instant-search UUID becomes available, read `provider`, `platform`, `route`, `http_status`, `credits_charged`, `safe_detail`, and `latency_ms` from `search_credit_ledger` for that `search_id` using an authorized read-only session. [Ledger implementation](https://github.com/sisisabia58/ELVsentiment/blob/feature/cari-sekarang/apps/worker/sentiment_monitor/instant_search.py)
2. For each route and query, capture ordered raw post IDs before app normalization, normalized IDs before app date and eligibility filters, and the final app-ranked IDs after those filters. Preserve provider ordering in the raw stage, rank the replay independently of dashboard labels, and record raw rows without extractable identities and date/eligibility exclusions alongside the capture. Use the same platform-specific identity at every stage. If the dashboard supplies a URL, map it to that identity using a stable permalink identifier and retain the reference URL outside the scorer input. A benchmark record appears in only one loss stage among raw absence, normalization drop, app exclusion and rank below the top ten.
3. Label all available top-ten posts manually from their text and source. Direct brand evidence names the brand in a mention, tag, or unambiguous variant. Brand-free generic coffee sales and unrelated cafés are weak for the brand case. The generic control accepts content directly about mobile or itinerant coffee, and the synthetic control should yield zero direct matches. Do not use the app’s rank or automatic relevance label as the benchmark judgment. Use the same platform-scoped direct `benchmark_ids` across compared routes and include manually labeled weaker items higher in the ranked order to diagnose ranking inversions.
4. Copy the fixture shape and set `provenance` to `staging` for verified sanitized measurements. Use the status `partial` for partially answered calls, `failed` for failed route captures and `unavailable` for unsupported coverage. Store latency and charged credits across the attempts and use `null` if measurement is missing. Record source, completeness, and warning codes under `coverage`. Keep per-attempt status, latency and credits in staging notes when comparing second pages. Strip credentials, authorization headers, signed URLs and any opaque tokens from committed data.

Run the scorer from the repository root.

```sh
python apps/worker/tools/search_route_benchmark.py apps/worker/tests/fixtures/scrapeatlas/search_benchmark.json
```

The scorer reads only a local file. Its synthetic fixture verifies stage separation, top-ten precision, recovery, rank inversions, and both controls. Synthetic IDs and the numeric timing and credit values exercise the scorer. They represent no provider measurements or dashboard records. Precision is the fraction of direct matches in the available top ten. The direct-match count and precision remain unknown if any top-ten post lacks a judgment. A successful empty page has zero direct matches and undefined precision. Benchmark recall is the fraction of in-scope reference IDs in the top ten and remains unknown when the reference set is empty. A failed or unavailable route leaves retrieval metrics unknown. Re-run with sanitized staging data to make a route selection.
